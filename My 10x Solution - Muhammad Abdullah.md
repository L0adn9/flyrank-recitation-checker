# My 10x Solution: Recite

**Repository:** https://github.com/L0adn9/flyrank-recitation-checker
**Track:** Backend AI Engineering · **Capstone:** Your 10x Solution

## 1. What is the problem?

People who memorise the Quran have to recite it **from memory** to find out whether they still know it. Reading along with the text does not work, because seeing the words hides your own mistakes. So someone has to listen: a teacher or a friend who knows the passage. That listener is usually available once or twice a week. In between, a skipped ayah, a wrong word or two ayahs said in the wrong order go unnoticed and settle into memory, and passages learned months ago fade, because revision is unplanned: people revise what they happen to remember, not what they are losing.

Who has this problem: students doing hifz between lessons, adults who memorised as children and want to keep it, and anyone learning a few surahs for prayer.

**The 10x claim:** getting a recitation checked goes from *waiting for the next lesson (days)* to *about 5 seconds*, any time, at no cost. You record yourself, and every skipped, wrong, repeated or out-of-order word is marked against the Quran text. A daily plan then tells you which passages to revise, based on your own mistakes.

## 2. How did I implement it?

**In plain words.** You pick a passage (say Al-Fil, ayahs 1–5), hide the text, press record and recite. The recording is uploaded and the API answers immediately with "queued". A background worker cuts the recording at your pauses, so that each piece is roughly one ayah, and runs an open Quran speech-recognition model (Tarteel's `whisper-base-ar-quran`, Apache-2.0) **locally** through whisper.cpp: no paid API, and the audio never leaves the server. The words it heard are compared with the expected words of the Tanzil Quran text by a weighted edit-distance alignment. That alignment names each difference: a wrong word (showing what you said instead), a missed word, an extra word, a repeat (a hesitation where you went back), or words in the wrong order. The page shows the passage in mushaf script with each mistake marked on the word. Every check also updates a per-ayah schedule (mistake: tomorrow; clean: after 1, 3, 7, 14, 30, 60 days), and a daily cron job turns what is due into a short revision plan. A PDF report shows accuracy over time, the most-missed words and where each surah stands.

**Measured:** on 13 test recordings with known mistakes (skipped, swapped, repeated and wrong ayahs, stopping early) every finding is correct: 13/13. Recognition runs at about 0.1× real time, so a 40-second recitation is checked in roughly 4–5 seconds; a recording that was heard before comes back from the cache in about 25 ms.

### The concepts (6 of 7, no swaps)

| # | Concept | How Recite uses it | Where in the code |
|---|---|---|---|
| 1 | API endpoints | FastAPI: auth, Quran text, attempts (audio upload), revision plan, progress, reports. Validation errors are 400; also 401, 404, 409, 413, 415 where they apply, and 202 for queued work | `app/main.py`, `app/routes/` |
| 2 | Database | Postgres (users, Quran text, attempts, transcripts, ayah progress, plans, jobs, reports) with versioned SQL migrations; data lives in a Docker volume and survives restarts | `app/db.py`, `app/migrations/` |
| 3 | Authentication | Email and password (argon2 hashes), JWT bearer tokens with expiry; every attempt and report is visible only to its owner (others get 404) | `app/auth.py`, `app/routes/auth.py` |
| 4 | Background jobs + cron | A job queue in Postgres (`FOR UPDATE SKIP LOCKED`, `LISTEN/NOTIFY`, retries with exponential backoff, permanent vs. retryable errors, recovery of jobs from crashed workers) runs speech recognition and PDFs off the request path; a daily cron (each slot runs exactly once, and a missed one is caught up) builds revision plans | `app/jobs.py`, `app/worker.py`, `app/cron.py`, `app/revision.py` |
| 5 | Reporting (PDF) | "My progress" PDF: accuracy chart, most-missed words, surah table, recent checks; built by the worker with headless Chromium | `app/report.py`, `app/templates/report.html` |
| 6 | Caching | Speech recognition is the expensive step, so transcripts are cached under the SHA-256 of the audio and the model name. Uploading a recording that was heard before is scored instantly in the API (201 instead of 202) without running the model | `app/checker.py`, migration `004` |

**Swaps:** none. The one concept not used is LLM integration, on purpose: recognition is done by a dedicated speech model, and the Quran text and its meaning must not be generated by an LLM. A test suite (50 tests, real Postgres) and a Docker Compose stack are included anyway.

**Non-goal:** Recite checks *which words* you said, not *how* you pronounced them: no tajweed grading. It is also not a mobile app.

## 3. How to run it

Requires Docker. From the repository folder:

```bash
cp .env.example .env          # then set POSTGRES_PASSWORD and JWT_SECRET in .env
docker compose up --build     # first build takes a few minutes (it compiles whisper.cpp)
```

Open http://localhost:8000 and sign in with the seeded demo account **demo@recite.test / demo-recite-2026**. It already has three weeks of practice history, a revision plan for today and data for the PDF. To try the checker without reciting yourself, `python3 scripts/make_samples.py` builds test recordings with known mistakes in `samples/`. Upload one with "or upload an audio file". The README has the full 5-minute demo path, running without Docker, and the tests.
